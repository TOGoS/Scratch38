*** 1.11. [[https://www.boot.dev/lessons/5cf07c09-fd73-4814-85b6-6bc6820914c6][Remote Server]]

This took me some tinkering (and talking to opencode itself) to figure out.
Here's the summary I eventually got out of it:

#+begin_quote
The distinction that actually matters is the flag, not the timing:

+ ~opencode serve --service~ :: registers itself; becomes the shared service; pair and bare opencode will use it.
+ ~opencode serve~ :: private, unregistered, invisible to discovery; only reachable via explicit --server + password.

So the hypothetical you'd want is "~serve --service~ first, then pair"
-- that's one registered service, one process, no
duplication. (Unverified: whether a second ~--service~ would refuse or
take over the registration. I'd expect takeover-or-fail, but I haven't
tested it.)

X "Two at once will likely mangle the database." Too strong, and
empirically already false -- both of these are writing to the same
opencode.db right now (the WAL picked up changes at 14:58 during this
chat) and nothing is mangled. SQLite in WAL mode is built for
multi-process access; writes serialize, and the DB stays consistent.

What you should actually avoid is narrower:

- Two servers driving the same session :: divergent in-memory state,
  interleaved writes, last-writer-wins on that session record. Not
  corruption, but a messy session.
- Two agents in the same working tree :: tool-level file races. This is
  the real practical danger, and it's a filesystem problem, not a
  database one.

So revised summary: one server per active session/working tree;
multiple servers are fine as long as they stay in separate lanes; the
registry -- not start order -- decides what pair and the TUI connect to.
#+end_quote

In summary:

#+begin_quote
- ~serve~ starts a server
- ~--service~ files it under ~service.json~ so clients find it
- clients auto-spawn a ~--service~ server only when the registry is empty or stale
- ~pair~ bridges a browser to whatever is registered.
#+end_quote

*** Tangent: how do sessions work?

#+begin_quote
How do sessions work?
Is it just sort of a transcript, so when I hand it over to 'the model',
it re-reads everything that has happened and takes that into account in the next response?
In which case changing models halfway through a session would be fine.
Or is there some kind of caching mechanism, possibly behind the scenes?
#+end_quote

DeepSeek V4.1 Flash Free, in my 'meaning of life' session, did some digging
(including spelunking in its own database and running some python), and said
(translation to orgdown by me):

#+begin_quote
Both, and the distinction is exactly where your intuition is fuzzy:
**the transcript is re-sent, and the caching is provider-side.**
There is no OpenCode-side "the model remembers."

**** What's actually stored

From exporting your own session (~ses_e33bd35c0ffe...~):

#+begin_src json
"info": { "model": {...}, "tokens": {"input":16716,"output":5174,
          "reasoning":10933,"cache":{"read":303104,"write":0}} }
"messages": [
  { "type":"user", "text":"What's the meaning of life?" },
  { "type":"assistant", "content":[
      { "type":"reasoning", "text":"The user asks a philosophical...",
        "native":{"reasoningField":"reasoning_content"} },
      { "type":"text", "text":"42, according to Douglas Adams..." } ],
    "snapshot":{"start":"36f6161...","end":"36f6161..."},
    "tokens":{"input":3619,"output":192,"cache":{"read":1792,"write":0}} },
  { "type":"idle" }
]
#+end_src

So a session is ~session -> messages -> content parts~ (text, reasoning, tool calls, files), plus per-message usage and a git snapshot for undo. Messages are never destroyed by compaction -- only stopped from being *sent*.

**** What happens each turn

The server rebuilds the request from scratch: system prompt + instructions + tool schemas + the whole visible conversation, re-serialized into whatever the current provider's API wants. Stateless from the provider's point of view, except where it uses native compaction.

Look at your session totals: **16,716 fresh input tokens but 303,104 cache-read tokens.** That's the whole story in two numbers -- the conversation is being resent every turn, and the shared prefix is being served from the provider's prompt cache instead of being re-billed.

**** The cache is a prefix cache, not a session cache

- Breakpoints are placed on the system prompt, the last tool
  definition, and the latest message (Anthropic-style
  ~cache_control~); other providers cache automatically.
- It keys on the **exact token prefix**. Append to the end ->
  cheap. Change something early (a system prompt edit, a model switch,
  an instruction file change) -> everything after it misses.
- Lifetime is provider-default (5 min on Anthropic) unless you set
  ~settings.cache.ttl~; ~warming: true~ sends throwaway requests to
  keep it alive across pauses.
- Compaction deliberately reuses the cache: it sends the full
  conversation for the summary so the summary request hits the same
  prefix.

**** Compaction is where "it re-reads everything" stops being true

Near the context limit, older turns get replaced by a summary plus ~15k of recent conversation:

#+begin_example
before   [ system ][ older conversation .......... ][ recent 15k ][ pending ]
after    [ system ][ summary + recent 15k ][ pending ]
#+end_example

So pre-compaction, yes, the model sees the literal transcript.
Post-compaction it sees a *summary* -- and the originals are still in the DB, just not in the request.
This is lossy and it's the main reason very long sessions drift.

**** So is switching models mid-session fine?

**Supported, yes. Free, no.** The stored format is provider-neutral, so ~/models~ re-serializes history for the new provider. But:

| What breaks                   | Consequence                                                                                                                                                                                   |
|-------------------------------+-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Prefix cache                  | Keyed by model/provider -> first turn after switch is a cold read; you pay full input price for the whole history once                                                                        |
| Native compaction checkpoints | Documented as provider+model-bound: switching "continues from the original conversation instead" -- i.e. the compacted checkpoint is discarded and you're back to a possibly-too-long history |
| Reasoning blocks              | Stored with provider-specific ~native~ metadata; foreign reasoning gets dropped or must be re-fitted (~reasoningField~, ~requireReasoning~) -- some fidelity is lost                          |
| Context window                | ~buffer~ is a *percentage* of each model's window, so a smaller model compacts sooner than you expect                                                                                         |
| Tool capabilities             | ~capabilities.freeform~/~tools~ differ per model; the same tools may not round-trip identically                                                                                               |

Warming also restarts after a switch, and background compaction is explicitly skipped "right after a model switch."

Practical upshot: switch at natural boundaries (before a big task, not mid-debugging-loop),
and expect the first turn to be the expensive one.
For same-provider same-family switches you mostly just pay the cold cache;
cross-provider is where the reasoning/compaction fidelity loss shows up.
#+end_quote

*** 3.5. [[https://www.boot.dev/lessons/8d8e80aa-2598-40ff-9659-3e2553025c14][Creating Custom Tools]]

They're written as TypeScript modules.

They export 'a plugin definition', looks like.
That object is created using ~Plugin.define~ where ~Plugin~ is defined in ~@opencode/plugin~,
which is passed a string ~id~ and an async ~setup(ctx)~ function that in turn
registers tools using ~ctx.tool.transform(tools) => { ... tools.add({...tool definition...}) ... }~.

Your tool has a ~name~, ~description~, ~input~ [schema], some ~options~, an ~execute~ function,
and, optionally, an ~output~ schema.  If no output schema, then the model can only
read a single ~content~ string of the output object.

If ~options: { codemode: true }~ (this is the default) then the agent will generate JavaScript to call
the tool and then execute this, which allows it to chain tool calls together.
~options: { codemode: false }~ forces the LLM to deal with the tool directly.

This exercise makes us install bun.

#+begin_src sh

#+end_src

Quite a bit of hemming and hawing was required to get the new tool to work.

The example did not make it obvious that the [Promise returned by the]
~execute~ method should always return a ~Tool.Result~ object which
in turn wraps the object whose shape is described by ~output~,
not that wrapped object directly.

In its final form, our ~.opencode/plugins/run-slop.ts~ looks like this:

#+begin_src typescript
import { Plugin } from "@opencode/plugin";

export default Plugin.define({
  id: "applymaxxing.run-slop-tool",
  setup: async (ctx) => {
    const cwd = ctx.location.directory;
    await ctx.tool.transform((tools) => {
      tools.add({
        name: "run_slop",
        description: "Run a SlopLang script with sloperator",
        input: {
          type: "object",
          properties: {
            path: { type: "string" },
          },
          required: ["path"],
          additionalProperties: false,
        },
        output: {
          type: "object",
          properties: {
            stdout: { type: "string" },
            stderr: { type: "string" },
            exitCode: { type: "number" },
          },
          required: ["stdout", "stderr", "exitCode"],
          additionalProperties: false,
        },
        options: { codemode: false },
        execute: async (input) => {
          const { path } = input as { path: string };
          const proc = Bun.spawn(
            ["uv", "run", "--no-active", "sloperator.py", path],
            {
              cwd,
              stdout: "pipe",
              stderr: "pipe",
            },
          );
          const stdout = await new Response(proc.stdout).text();
          const stderr = await new Response(proc.stderr).text();
          const exitCode = await proc.exited;
          return { output: { stdout, stderr, exitCode } };
        },
      });
    });
  },
});
#+end_src
