** [2026-11-26 Thu] - Distilled notes from the OpenSCADDesigns session - Master Qwen (Qwen3.8 Flash)

*** Verdict on TDBuilder-as-roll-your-own

Defensible and, in this case, correct: domain-heavy rules are
*programs*, and 'build system as library in a real language' is
exactly Mill's pitch (independent convergence noted; Shake is the
Haskell proof the design space is respectable).  Generic tools
were never really the competition: `just`/`task`/`mage` have no
dependency graph; Ninja is a backend worth adopting *as a
dependency* only if the graph ever outgrows one file; Bazel's
hermeticity buys nothing for a single-user artifacts-as-
historical-record repo.  Failure modes to watch for, none present
yet: multi-user, multi-language, or feature creep into remote
caching.

*** The core tension TDBuilder lives in

mtime staleness is cheap and fits 'don't re-render 600 parts',
but mtimes record last-write-of-bits, not last-build.  Ninja
papered over the same gap with `deps`/`restat`; the honest
endgame is content-keyed actions (Bazel-style), which for a
render farm just means 'rerun everything' unless you add caching
-- at which point you rebuild TDAR anyway.  Sequencing per TOGoS:
extract TDAR, then mtime (and its workarounds) stops mattering.

*** Built-marker scheme (landed in OpenSCADDesigns master)

- Hardlinks/copies report the source's mtime; `x:Hardlink` writes
  a `.<name>.built` sidecar, consulted via TDBuilder's
  `mtimeFunction` hook as max(file mtime, marker mtime) -- the
  marker may only *raise* the effective build time, never mask
  what the filesystem knows (hand-restamped targets).
- Missing target returns undefined so the builder's own stat
  yields 'not found'; an orphaned marker (file gone) warns once,
  never fabricates up-to-date-ness.
- Precedent: `mtimeFunction` was added circa 2021 precisely
  because TDAR-cached artifacts had untrustworthy mtimes (see
  `SynthGen2100/P0019/packages/sgutils@0.1/tdarx/openscad.ts`
  reference in OpenSCADDesigns make.ts).  Same workaround family
  as Make idiomatically using marker files, and tdbuilder's own
  `touchDir`.

*** The real gap (highest-value fix)

Prereq lists are just the input .scad text; `use()`-ed libraries
(TOGPath1.scad et al.) are invisible to the graph.  This is the
`-MMD` depfile problem, unsolved since the '90s in this repo, and
the only place the system is less correct than '90s technology.
TDBuilder already has the seam: `fetchGeneratedTargets()` is the
built-in hook for a dynamic dependency-discovery pass (scan
`use()`/`include()` lines, emit library-to-dependent edges).
Until then, shared-library edits rebuild nothing.  (Renders being
historical artifacts mitigates but doesn't excuse it: --no-scad-reruns protects
recorded bits, not build correctness.)

*** Content-addressing plan, as stated (2026-11-26)

Take a .scad plus context, refer to it by
`x-git-object:<sha>#<path>`, recursively rename imported libraries
by content hash, derive a reliable identifier for the file, cache
build results by those hashes instead of mtimes.  Implemented once
as TDAR (Deno Active URI Resolver), worked well, last used circa
2021, code presumably on the SynthGen box (not this machine --
searched 2026-11-26).  Extraction blockers are all the
planning-shaped ones: where the code lives/should live, naming,
where the ontology gets documented.  TSoft40 seeded as the
decision-documenting venue; S0040 (this repo) as the think-space.

*** Test-.scad version policy (discussed, deliberately unimplemented)

All 2023/test files pass under 2021.01 today.  Recommendation when
a file first needs otherwise: in-file directive (`// build:
openscad=20261031 features=manifold`), parsed by the runner,
vocabulary mirroring make.ts's CLI tokens, unknown tokens are
errors, unmarked files warn rather than silently defaulting.
Rejected: filename encoding (constraint churn = rename churn),
sidecar JSON (workable -- osdBuildRules already reads .json
per-name metadata -- but one hop away from the thing it
constrains), separate make.ts rules (adequate, invisible to
whoever edits the .scad in the GUI).

** [2026-11-28 Thu] - Some Thoughts - TOGoS

Build systems and programming languages.  And music stuff.
There's a lot of overlap between the domains in my thoughts
so I kind of want to use this scratch space to dump them
out and let the AI agents help me figure out where to put them.

Primers (find as subdirectories of ~proj~):
- TOGVM-Spec :: RDFish language
- TOGETL :: Lots more RDF!  For data rather than for programs.
  Contains some attempt to start consolidating schma info in one place.
- TSoft40 :: General aspirations
- TScript34 :: Collection of language interpreter scratch spaces;
  TScript34.2 (~P0002~; this project predates my 'keep-things-in-isolated-histories' practice,
  so it's actually a subdirectory, but check for branches.)
- TScript34 the language :: Not everything in the TScript34 project is about this language.
  When I talk about the TScript34 language I mean the line-based concatenative one
  implemented by the interpreter in TScript34.2 (and in some other spots).
- MapTranslator35 :: Uses TScript34 scripts as an interchange format;
  to treat a script as encoding a value you interpret it and
  the value is what's left on top of the stack.
- SynthGen2100 :: Contains code for TDAR, the build tool.
  It should be separated out into its own project, but hasn't yet been.
- [[https://www.nuke24.net/docs/2014/CoolCereal.html][CoolCereal]] :: stack-based bytecode format for defining objects
- [[https://www.nuke24.net/docs/2023/TS34EncodedDatatype.html][The 'TS34Encoded' datatype]] :: allows one to unambiguously talk about values represented by resources;
  TScript34 uses these internally to lazily pass around concepts;
  "the object described by the resource that you'd get if you concatenated data:,foo and urn:sha1:BLAHBLAH together"
  is a first-class value in TScript34.
- MCAS-ND :: Multi-Channel Audio Signal, N-Dimensional;
  Used both by an experiment in SynthGen2100, and by the map translator
  tool which uses TScript34.2

Thought is on wanting a unified language for expressing data
transformations.  Same domain as TScript34[.2].

Some use cases:

- CSG pipeline (Scratch38-S0039, but keep going to support boolean
  operations, signed distance function representations and conversions
  to/from meshes, what have you)
- Audio pipelines
  - Mix two streams together
  - Concatenate audio chunks

Features:
- Rarely do we work on 'files', bur rather resources, which might be backed by files, or HTTP services,
  but might also be abstract
- Explicit differentiation between conceptual objects and the byte streams that encode them
  - Use XML datatypes or encoder/decoder references (also by URI)
- Resource references as first-class values :: reference resources by bitprint URN and transparently operate on them
- Laziness :: Don't calculate results until needed
- Purity :: Reads by hash URN are pure; writes are generally done 'outside' the program;
  the pipeline provides a result (usually 'whatever's on top of the stack at the end')
  and then the wrapping program can..write it to disk, or output to STDOUT,
  or whatever.  But in general we only do that at the top level!
  - Note: As of writing, Scratch38-S0039 has a 'write' operator;
    now that we've got that system working I would like to move away from it,
    hence recent suggestions (did we implement it?  I actually forget)
    to decouple decoding/encoding from reading/writing files.
  
Some options for 'the language':

- TScript34?
- [[#2025-11-26-tscript44-initial-thoughts][TScript34-like language]] (perhaps using Tcl-like ~{...}~ to allow spaces in tokens)?
  - Let's blow a TOGSOFT number: call it ~TScript44~.
- TOGVM structure?
- Forthlike as interface -> compiles to TOGVM internally?
  - That's fine, but should the TOGVM RDFish JSON-encoded stuctures
    be the interchange format, or should we leave the Forthlike language
    as the interchange format?
- Some existing programming language
  - But I want it to be *embeddable* in various contexts, not assuming
    JavaScript / Java or any other ecosystem, hence the draw of a DSL.
  - Fine for an interpreter to be written in a regular language!
    But I want to be able to express as much of the high-level logic
    as possible using the common language
  - This is important because data transformations are themselves data
    that we need to be able to pass around if we're going to
    store or transfer references to computed values
    without actually computing them, first!
- For ASTs, there are some options other than RDF or JSON:
  - Active URIs (quite handy; TDAR uses them)
  - A Lisp
  - That said, if I want to have a well-defined mapping to some structure
    that's defined in RDF terms, and we're just talking about a user-friendly
    language that compiles to that, something minimal/concatenative
    being the 'feels good' language and then the RDF+XML (or active URI)
    representation being the "proof that we can represent our programs that way"
    seems like a good way to split the effort.

Forthlike might be more concise than serialized ASTs (the TOGVM approach,
which I've never really implemented), and remove a layer of translation.
And I do keep coming back to the idea; there is something soothing
about concatenative languages, especially for data transforming
pipelines (but of course).  It's nice when program can be trivially
encoded in $argv.  Maybe there is something to it.

*** A new language? (TScript44)
:PROPERTIES:
:CUSTOM_ID: 2025-11-26-tscript44-initial-thoughts
:END:

I'm thinking basically Scratch38-S0039's language,
but to allow operation names with spaces in them in a script
(as opposed to argv, where it's already delimited),
we can use Tcl-style nestable curly braces.

#+begin_src
ns:some-op
{ns:some-op-constructor arg1 arg2 and so on}
#+end_src

Lots of flexibility.

TScript34 programs could be encoded with this same syntax!
Just replace 'lines' with curly-brace delimited tokens.

Everything-is-[at some point]-a-string is a very easy escape hatch.
Want to stick a JSON value in there?  Call your operator ~json-value:{"name":"Fred"}~ and there you go.

TScript34 namespaces the shit out of operations and encourages one to define aliases to make your program less unreadable.
This is cumbersome for one-liners (as used by Scratch38-S0039), but I think it's a good principle;
if needed we can define some 'implied preamble' (or whatever Rust calls it; same idea).

So things I'd change from TScript34 to the new language:
- Curly braces instead of lines
- Possibly: More flexible operator constructor call syntax;
  - TScript34 wants all operands to be resource names,
    but this makes expressing an operation that pushes a literal string a little cumbersone,
    since in addition to the operator name (a URI), the data to be pushed is also a URI.
  - Scratch38-S0039's operation names can include `:`
    (and perhaps a different delimiter should be chosen, like `::`,
    so that `;`-separated options don't need to percent-encode single colons,
    making URIs in options a little prettier)
    followed by free-form string.
  - If we're betting on nestable curly-brace-delimited strings,
    perhaps this opens up more nestable/flexible/uniform way
    to allow free-form syntax.

I wonder if "~{{literal string here}}~" would be a reasonable shorthand for literal strings,
since ~{~ would not be a valid first character in a URI-like identifier for an operator/operation,
it seems reasonable to overload that one for that very common case.
The closing ~}~ gives an opportunity to provide 'datatype'...either with a ~^~ (as in Turtle)
or ~|~ (as in TGETLTSV) or just whitespace (as in TScript34-encoded values).
Beginning with special characters is valuable real estate, so maybe don't claim it right away.
